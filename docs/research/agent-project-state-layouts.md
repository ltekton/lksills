# Coding-agent project state layouts

Research snapshot: official documentation plus first-party source checked against the pinned repository commits below. Documentation URLs are mutable; source links are pinned. “Not verified” below means the primary sources reviewed do not establish the claim, not that an implementation cannot contain it.

## At a glance

| Agent | Global root and override | Project grouping/key | Conversation/state format | Project-local files intended for sharing |
|---|---|---|---|---|
| **OpenAI Codex CLI** | `~/.codex`; `CODEX_HOME` | Rollouts are date-partitioned and carry `cwd`; the SQLite state model has explicit project IDs, project roots, and `threads.project_id` | JSONL rollouts plus several SQLite databases | `AGENTS.md` chain, trusted `.codex/config.toml`, and repository `.agents/skills/` |
| **Anthropic Claude Code** | `~/.claude`; `CLAUDE_CONFIG_DIR` | Transcripts use a sanitized project-path directory; auto-memory uses a repository-derived project directory, shared by worktrees/subdirectories | JSONL transcripts; JSON settings; Markdown auto-memory | `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/settings.json`, `.claude/rules/`, `.mcp.json`, and project skills |
| **Pi** | `~/.pi/agent`; `PI_CODING_AGENT_DIR`; sessions additionally have `PI_CODING_AGENT_SESSION_DIR`/`--session-dir` | Stable sessions use a reversible-ish sanitized absolute cwd directory and record the original cwd in the header; trust uses canonical path keys | Stable sessions are JSONL. Experimental durable sessions use `session.sqlite` | `.pi/settings.json`, `.pi/mcp.json`, prompt/system/resource files, and project context files |

## OpenAI Codex CLI

**Roots and overrides.** The official config guide says user configuration is `~/.codex/config.toml` and that project configuration is `.codex/config.toml`; the official source resolves the home to `~/.codex` unless `CODEX_HOME` is set. `CODEX_HOME` must name an existing directory and is canonicalized ([config basics](https://developers.openai.com/codex/config-basics); [home-dir source](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/utils/home-dir/src/lib.rs)).

SQLite has a separate root. The config reference documents `sqlite_home` as the directory for Codex’s SQLite-backed state DB. The current source uses an explicit `sqlite_home` config value first, then `CODEX_SQLITE_HOME`, then `CODEX_HOME`; a relative environment value is resolved against the current working directory ([config reference](https://developers.openai.com/codex/config-reference); [resolution source](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/core/src/config/mod.rs); [config type](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/config/src/config_toml.rs)).

**Project grouping and SQLite.** Codex’s primary conversation artifacts remain JSONL rollouts under `$CODEX_HOME/sessions/<year>/<month>/<day>/` (with `archived_sessions` for archived data); each rollout begins with `SessionMeta`, including `session_id`, thread IDs, and `cwd` ([rollout constants](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/rollout/src/lib.rs); [session metadata](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/protocol/src/protocol.rs)). Thus the physical rollout directory is time-keyed, not project-keyed; project association is metadata/indexed state.

Codex does use SQLite for local runtime/index state. The state crate describes itself as extracting rollout metadata from JSONL and mirroring it into SQLite. The current database filenames include `state_5.sqlite`, `thread_history_1.sqlite`, `logs_2.sqlite`, `queue_1.sqlite`, `goals_1.sqlite`, and memory databases. The schema has `projects`, `project_roots`, and `threads.project_id`, with an index for project thread listing. The config reference specifically describes `sqlite_home` as holding the state DB used by agent jobs and other resumable runtime state ([state crate](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/state/src/lib.rs); [SQLite paths](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/state/src/sqlite.rs); [project migration](https://github.com/openai/codex/blob/402f5b6fdf28a7a72c153dbe6fe01e252205d7d6/codex-rs/state/migrations/0049_projects.sql)).

**Project-local/checked-in boundary.** The official docs describe repository `AGENTS.md` files as project instructions, with optional nested `AGENTS.override.md`; the global instruction file lives under Codex home. Trusted project `.codex/config.toml` layers are read from the project root toward the current directory. Repository skills are discovered from `.agents/skills` up to the repository root, and the docs explicitly describe those as skills teams can check in ([AGENTS.md guide](https://developers.openai.com/codex/guides/agents-md); [config basics](https://developers.openai.com/codex/config-basics); [skills locations](https://developers.openai.com/codex/skills)). Disposable rollouts, SQLite state, logs, and credentials are outside the project root by default.

## Anthropic Claude Code

**Roots and overrides.** The official documentation states that `~/.claude` is the default configuration directory and that `CLAUDE_CONFIG_DIR` moves settings, session history, and plugins under another root. `CLAUDE_CODE_PROJECT_DIR_NAME`, used together with `CLAUDE_CONFIG_DIR`, lets a host choose the project directory name instead of deriving it from the working directory ([environment variables](https://code.claude.com/docs/en/env-vars.md); [sessions](https://code.claude.com/docs/en/sessions.md)). Auto-memory has a more specific `autoMemoryDirectory` settings override ([memory](https://code.claude.com/docs/en/memory.md)).

**Project grouping and files.** Claude Code documents transcripts as JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`. By default `<project>` is the whole working-directory path with non-alphanumeric characters replaced by `-`; names over 200 characters are truncated and suffixed with a hash. Auto-memory uses `~/.claude/projects/<project>/memory/`, but its `<project>` is derived from the Git repository, so worktrees and subdirectories share memory. `CLAUDE_CODE_PROJECT_DIR_NAME` replaces that derived name when the custom-config-root mode is used. The docs also identify `~/.claude.json` as a separate machine-local JSON file holding sign-in state, MCP configuration, and per-project state such as trust decisions ([sessions, transcript layout](https://code.claude.com/docs/en/sessions.md); [memory, storage](https://code.claude.com/docs/en/memory.md); [settings and `.claude.json`](https://code.claude.com/docs/en/settings.md)).

**SQLite.** The official documentation reviewed specifies JSONL for transcripts, JSON for settings/configuration, and plain Markdown files (`MEMORY.md` plus topic files) for auto-memory. It does not document a SQLite database or a SQLite override/use. The official `anthropics/claude-code` repository is not the product implementation (the pinned snapshot is documentation, examples, and release material), so SQLite use cannot be ruled out from the public sources; it is simply **not verified** here ([official repository at `2bfb629dfaff0c8318047a4beb93cf1dc5b58b18`](https://github.com/anthropics/claude-code/tree/2bfb629dfaff0c8318047a4beb93cf1dc5b58b18)).

**Project-local/checked-in boundary.** Claude’s docs explicitly mark shared project files as committed: `CLAUDE.md`/`.claude/CLAUDE.md`, `.claude/settings.json`, `.claude/rules/`, project skills, and root `.mcp.json`. They explicitly describe `.claude/settings.local.json` and `CLAUDE.local.md` as personal/gitignored; auto-memory is machine-local and outside the repository. This is a particularly clear separation between portable project intent and disposable per-machine state ([`.claude` directory](https://code.claude.com/docs/en/claude-directory.md); [settings scopes](https://code.claude.com/docs/en/settings.md); [memory scopes](https://code.claude.com/docs/en/memory.md)).

## Pi

**Roots and overrides.** Pi’s official coding-agent docs define the user agent directory as `~/.pi/agent`, overridable by `PI_CODING_AGENT_DIR` (or SDK `agentDir`). Session storage is independently overridable by `PI_CODING_AGENT_SESSION_DIR`, `sessionDir`, and `--session-dir`; the CLI flag wins. The stable user directory contains settings, auth, models, extensions, skills, prompts, themes, and sessions ([configuration](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/docs/configuration.md); [environment variables](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/docs/environment-variables.md); [CLI](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/docs/cli.md)).

**Stable session grouping.** The default stable path is `~/.pi/agent/sessions/--<path>--/<timestamp>_<session-id>.jsonl`. The implementation resolves the cwd, removes the leading separator, and replaces `/`, `\\`, and `:` with `-`; the JSONL header retains the original `cwd`. This groups sessions by launching directory without putting session content in the project. `trust.json` is also global and keyed by canonical absolute paths, with nearest-parent lookup, so trust is grouped by directory hierarchy ([session format](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/docs/session-format.md); [path implementation](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/src/core/session-manager.ts); [trust implementation](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/src/core/trust-manager.ts)).

Pi’s stable session format is JSONL, with tree links (`id`/`parentId`) and extension `custom` entries for state reconstruction. The stable implementation and package dependencies contain no SQLite use. However, the same official repository has clearly labeled **experimental** durable/service slices: they store one `session.sqlite` per session, under a cwd hash such as `~/.pi/agent/experimental/durable-sessions/<cwd-hash>/<session>/session.sqlite`, with `meta.json` holding the original cwd. That SQLite is for durable Harness/conversation state, streamed partials, tool output, queues, and restart recovery—not the stable Pi session format ([stable format](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/docs/session-format.md); [experimental durable design](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/src/experimental/durable/README.md); [experimental session path](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/src/experimental/durable/sessions.ts)).

**Project-local/checked-in boundary.** Pi’s project `.pi` directory contains settings, MCP configuration, system-prompt files, extensions, skills, prompts, and themes. Context files (`AGENTS.md`, `AGENTS.override.md`, and `CLAUDE.md`) remain ordinary project/ancestor files. Pi’s docs classify these as project resources and gate most of them on project trust; they do not label each one “committed,” so the safe inference is that they are project-local configuration candidates, while session JSONL, `trust.json`, credentials, and the user agent directory remain outside the project by default ([configuration](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/docs/configuration.md); [project trust](https://github.com/badlogic/pi-mono/blob/8c911797c3b6b5d3b3921ce4d2438e98e1a948a6/packages/coding-agent/docs/security.md)).

## Related precedent: mise

Mise keeps four categories separate rather than placing all application files beneath one home. Its documented defaults and overrides are:

| Category | Default | Direct override |
|---|---|---|
| Configuration | `${XDG_CONFIG_HOME:-$HOME/.config}/mise` | `MISE_CONFIG_DIR` |
| Cache | `${XDG_CACHE_HOME:-$HOME/.cache}/mise` on Linux; `~/Library/Caches/mise` on macOS when XDG is unset | `MISE_CACHE_DIR` |
| Local state | `${XDG_STATE_HOME:-$HOME/.local/state}/mise` | `MISE_STATE_DIR` |
| Installed data | `${XDG_DATA_HOME:-$HOME/.local/share}/mise` | `MISE_DATA_DIR` |

The documentation explicitly says to keep these directories separate. Global authored configuration is normally `config.toml` in the configuration directory. Mise stores trust records and tracked configuration paths in the state directory, installations and plugins in the data directory, and disposable metadata in the cache directory. Its generated global lockfile is also portable configuration-adjacent state: `mise lock --global` writes `mise.lock` beside the global config under `~/.config/mise`, and the documentation expects configuration and lockfiles to be versioned together. This supports separating files by lifecycle rather than treating one relocatable application home as a suitable default ([directory documentation at `171902a`](https://github.com/jdx/mise/blob/171902a41a637aeea04ee8ca7327c42cc3c42850/docs/directories.md); [global lock CLI at `171902a`](https://github.com/jdx/mise/blob/171902a41a637aeea04ee8ca7327c42cc3c42850/docs/cli/lock.md); [trust CLI at `171902a`](https://github.com/jdx/mise/blob/171902a41a637aeea04ee8ca7327c42cc3c42850/docs/cli/trust.md)).

## Design implications

### Verified facts to carry forward

1. All three separate project-scoped intent/configuration from machine-local conversational state. Codex and Pi make the default session root explicit; Claude documents both the root and project-directory naming rules.
2. A project key needs more than a display name. The agents preserve or derive an absolute/canonical path, repository root, or explicit project roots, and they keep the original cwd in metadata. Worktree behavior is an explicit policy: Claude’s auto-memory shares across a repository; Pi’s default sessions are cwd-specific.
3. JSONL remains a practical append-only transcript/source format. SQLite appears where indexed queries, resumable runtime state, queues, or durable recovery are needed (Codex; Pi’s experimental durable mode), not as a universal requirement.
4. Checked-in files are human-authored instructions/configuration and portable skill/resource sources. Session transcripts, trust decisions, credentials, caches, logs, generated projections, and local overrides are machine-local or disposable.
5. Mise provides the closest package-manager precedent for filesystem placement: authored global configuration and its portable lockfile live under the configuration root, while trust and tracking are state, installed objects are data, and disposable fetch metadata is cache. Independent `*_CONFIG_DIR`, `*_STATE_DIR`, `*_DATA_DIR`, and `*_CACHE_DIR` overrides preserve those lifecycle boundaries.

### Recommendations for lskills

- Give machine-local state an explicit, overridable root such as `LSKILLS_STATE_DIR`, with a documented XDG default. Keep configuration, state, durable data, and disposable cache under separate roots rather than one application home. Never default clone caches, staging, receipts-under-construction, or indexes into the lskills source root.
- Keep the portable boundary strict: `.lskills/project.toml`, `.lskills/lock.toml`, authored skill trees, and any deliberately shared project configuration stay project-local; source caches, temporary materialization, operation logs, crash recovery, and per-machine receipts live outside it. Do not make a generated deployment projection the source of truth.
- Use a canonical project/workarea identity plus a collision-resistant filesystem encoding or hash, but retain the original canonical path and (where relevant) repository/worktree identity in metadata. Decide explicitly whether sessions and caches are per workarea, per repository, or per worktree; do not let a sanitized directory name accidentally decide semantics.
- Start with append-only JSONL or small JSON/TOML records for inspectable operation history. Add SQLite only for a demonstrated query/concurrency/recovery need; if added, separate the DB root override from the general state root, version migrations, and provide repair/backup behavior. Treat SQLite as an index/runtime store, not the only copy of user-authored portable state.
- Make “project-local and checked in” versus “local-only and ignored” a documented contract for every file, including lockfiles, receipts, staging remnants, and per-project authorization/trust. This is the clearest reusable lesson from Claude Code’s explicit shared/local split.
